# M06-R 规模复测

## 方法

在同一台 Windows 11 实机（Intel Core 5 220H，12 核 16 线程，约 31.5 GiB 内存）串行使用 Python 3.12.9 和随附 SQLite 3.45.3。SQLite `user_version=7`。本轮复测使用同一组物理 SQLite 夹具的独立备份作为每个路径的起点。千条及万条夹具通过 M04 导入、M05 审核和 C3 分段构建。十万条夹具复用 C5 在第一次合成来源许可撤销后的已验证备份。所有输入、回执和身份均为合成，真实研究 API 调用为 0。

对每档规模分别执行批量复核和逐条复核，每条路径记录一次新建 SQLite 连接及连续五次热读取。构建和复查会预热系统文件缓存，未测操作系统冷盘。样本 P95 采用包含端点的线性插值。SQL 计数使用单独一次 `sqlite3` trace，包含通过 Python 连接执行的顶层语句，不展开 SQLite 查询计划内的子查询。阶段计时另取单独样本。峰值工作集是测试 Python 进程在对应规模结束时的累计峰值。

仓库中的规模测试可以重建等结构的合成夹具，并执行同类热读、SQL 跟踪、筛选、撤销和恢复。完整重建的 100K 导入批次布局与本次复用的旧夹具可能不同。下面的命令生成新夹具和本机报告。

```powershell
.\.venv\Scripts\python.exe -m scripts.benchmark_m06_denominators --sizes 1000 10000 100000 --repeats 5 --work-directory ..\m06-r-local --report ..\m06-r-local\replay.jsonl
```

基线代码为 `7b26d8da89db636c7e3f4ad73490b53dcc555155`。历史耗时见 [C5 规模记录](../m06-c5/scale-benchmark.md)。本次三档和两种路径均串行运行，候选独占本机测试窗口。比较去掉响应 `as_of_utc`，保留其余结构，包括统计、对账、排除账、版本、覆盖状态和异常引用。

2026 年 11 月 25 日，基线十万档与 M04 专项复测有短暂重叠。专项工具窗口为 UTC 08:40:51–08:41:02，测试自报 3.115 秒。基线日志没有样本级绝对时标，无法判定专项复测影响了资格、热读还是恢复。基线恢复阶段已单独计时的子步骤至少耗时 225.245 秒，结果在 UTC 08:47:24.749 写入，复算可得恢复最迟于 UTC 08:43:39.504 开始。两次浏览器探测日志于 UTC 08:44:39.240 和 08:45:05.430 建立，处于恢复窗口，晚于热读。重叠负载对恢复各阶段的耗时影响未知。

## 实际查询计划

旧 `IN` 批量路径在 500 个绑定键的 SQLite 计划中先用 `import_batches_by_study` 取项目批次，再用 `(batch_id, line_number)` 索引的前缀遍历批次行。每组键均可能重复扫描同一批次。逐条路径直接用 `import_rows(record_id)` 唯一索引。候选批量路径以 `json_each(:record_ids)` 提供有界键集，通过 `CROSS JOIN` 在相同索引查找每条记录，随后按主键关联批次、来源、范围及项目。两条路径共享原资格策略、当前审核及许可检查、保留期限、同文件副本与来源撤回检查。

候选仍使用单次统计读事务。快照失效检测、UTC 日期复核、权限撤销复核及结果重试由既有流程处理。性能改动不创建持久化缓存、物化视图或数据库版本。

## 恢复验证

每档规模在统计读快照与写事务竞争时撤销第二条合成来源许可。测试确认写事务等待 SQLite 写锁，提交后读请求重新取得有效快照。强杀已开启写事务的子进程，确认其未提交的标志行未落盘。独立备份到另一临时库，重新打开并执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`。对照撤回后现场与恢复库的全量响应，并验证历史版仍适用当前许可。

## 剩余瓶颈

十万档批量资格核验和投影用了 32.164 秒，占插桩总耗时约 81%。资格复核仍需读取当前许可、审核、撤回和同文件副本。需求发生的转载链和依赖证据可能按项解析，读取时保留核验原话区间所需的快照投影。合成夹具包含转载与多份支持证据，未模拟高密度真实审核历史或高并发读请求。

十五秒是全范围查询的探索目标。后续 M13 若需交互式大范围统计，先测同证据限制下的常见窄范围查询。任务化或增量方案需单独审定，并定义授权和来源许可变化后的失效边界。
