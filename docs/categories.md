# 意图 ↔ 大类双向模型

> 决定（2026-11-23，Ryan 定）：工作台是全品类的，不是营养秤专用的。
> 一个意图可以属于多个大类，再定一个主大类。大类本身也可以被发现，不只预设。
> COSORI 营养秤只是第一个跑通的品类。

## 双向查找

| 方向 | 搜什么 | 跳出什么 |
|---|---|---|
| 意图 → 大类 | 搜一个意图，如“少拿手机” | 它属于哪些大类，主大类排第一，其次大类随后，每个归属都带理由与证据 |
| 大类 → 意图 | 搜一个大类，如“备餐管理” | 这个大类底下不同的用户意图，每个意图带定义、证据 n 与代表原话 |

仪表盘上这是一张意图与大类的双向索引，两个方向都能点进去、下钻到原文与批次。

## 字段规则

- 每个意图一条注册表记录，带 `category_ids`（所属的全部大类）与
  `primary_category_id`（唯一主大类），见 `schemas/intent-registry.schema.json`。
- 每个大类一条记录，带名称、定义、包含 / 排除标准、来源（预设或发现），
  见 `schemas/category.schema.json`。
- 一个意图归属多个大类时，每个归属都要写理由与证据（`category_assignments`），
  不能只挂一个名。
- 计数口径：汇总、合计、趋势一律只按主大类算，其次大类只在下钻时展示，
  不得相加、不得重复计数。这是“定性不推比例”红线的延伸：一个意图挂两个大类，
  不等于两个意图。

## 大类怎么来

- 预设：研究开始前先定一批大类，作为第一轮的落点。
- 发现：跑出来一堆意图都塞不进现有大类时，长出一个新大类，而不是硬塞。
  新大类要写定义、包含 / 排除标准与触发它的意图清单，经人工确认后入表并升版本。
- 合并与拆分留变更记录，大类只升版本、永不静默改写，与意图注册表同一治理方式。

## 与发现层的关系

- 发现层提候选意图时，同时建议它属于哪些大类（主大类 + 其次大类），
  人工确认时一起定。
- 候选意图进不了任何现有大类，是新大类的信号，进候选池时标注“疑似新大类”，
  不直接建大类。
- Jev 编码时，Choice 选项仍是意图清单；大类不作为 Jev 的直接分类目标，
  大类归属是注册表层面的结构，不进 Jev 问题。

## 与问卷的关系

- 按大类出题时，题目选项来自该大类下的意图清单；一个意图挂多个大类，
  在不同大类的问卷里可以重复出现，但回收分析时按意图归一，不重复计数。
