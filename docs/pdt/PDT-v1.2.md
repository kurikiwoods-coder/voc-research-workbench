## 1 背景与问题定义

目前的用户洞察靠人工在搜索引擎、品类论坛、视频评论、Reddit 和 Amazon 中查找内容，再凭经验归纳需求。问题：检索路径随人而变、网页摘要易被当成原话、样本抽取不透明；新意图缺少发现与验证机制；数据进入分析后缺乏来源可追溯与复跑能力。

- 发现不了清单之外的意图：人工编码和现成分类工具只能把内容往已有的框里分。
- 规模化不了：站外讨论、论坛长帖、CSV 评价动辄成千上万条，人工逐条读只能抽样；抽样口径靠记性，不同批次不可比。
- 发现与验证脱节：定性发现做完后另起一份问卷验证，题目与发现之间没有系统映射，验证结果也不回流。

Amazon 评价保持受限补充来源定位，不新增自建批量爬虫。主线是跨平台公开讨论的发现与经授权的原文获取；搜索引擎用于找 URL，站点 API/授权提取/人工上传用于取得原话。新闻、评测文章和搜索摘要只作为背景或线索，不进入"真实用户声音"的主统计口径。

与既有资产的关系：已发布的三语 Google Forms 投票问卷是问卷输出模块的现成投放通道与题型参照（先 2–3 人试填、再群发；只分享填写链接）；既有站外证据表与竞品评价编码表可作首批 CSV 导入的历史语料；既定方法论直接写进系统约束（公开 US verified 购买评价为产品体验主要依据；定性结论不推用户占比；内部数据纯负面只做痛点排序；旧款结论不套新款；口径不一致的数字绝不并列引用）。

## 2 目标、非目标与成功标准

目标：G1 发现清单外新意图（意图注册表）；G2 对给定意图清单规模化、可校准、可复核编码（统一数据表 + Jev 执行层）；G3 情感/问题/趋势/推荐集中在一个仪表盘；G4 把发现直接生成验证型问卷并投放，回收回流。

非目标：不做 Amazon 爬虫，不买代爬服务；不做产品路线图与需求优先级管理；不采购企业级主题分析平台；不把模拟数据、模拟投票或生成模型预估答案当作真实用户结论；不做用户画像合成与买家占比推断。

成功标准（P0）：发现成立（盲测集上识别新意图候选并证明人工确认/驳回机制可用；真实研究中如没有可靠新意图，允许输出"本轮未发现"，不得强行创造）；执行成立（Jev 在 100–200 条人工金标准上完成校准，分别报告 Choice Macro-F1、Score 分档一致性、Noul 逐项 F1；阈值/版本记录齐全）；出题成立（由人工确认的候选意图或已确认痛点生成至少 1 道验证题，经真人试填后可导出 Google Forms）；可追溯（所有正式 VOC 结论必须回到用户原话、合法保留的证据、来源 URL、检索任务及采样批次）。

## 3 用户与使用场景

目标用户：研究者（主用户，导入与检索语料、确认候选意图、审阅仪表盘、生成与投放问卷、导出洞察报告）；标注者（标注 100–200 条金标准、处理低置信复核队列，P0 可由研究者兼任）；决策读者（只读洞察报告与仪表盘结论页）。

核心场景：S1 发现新意图；S2 评估产品体验（上传一批 CSV 评价，Jev 批量编码）；S3 日常洞察巡检；S4 生成验证问卷；S5 竞品对照（P2）。

试点场景锚点：核心卖点是常吃食品先在 App 里设好，日常称量时直接在秤端选择、称量并查看对应份量的热量、蛋白质等营养信息，减少重复称量时对手机的依赖。

## 4 数据源规格

每个来源接入前必须登记接入方式、回答什么问题、证据等级、口径红线。证据等级：A = 可作主要依据；B = 对照与三角验证；C = 只作信号或痛点排序，不推比例。

| 来源 | 接入方式 | 等级 |
|---|---|---|
| 全网公开讨论（核心发现入口） | Tavily + Brave 等搜索 API：AI 生成查询组合、发现 URL；按站点权限获取原文 | 条件 A：原话可核验；否则 C 线索 |
| 垂直论坛 / 开放社区（主线原话） | 可访问的论坛官方 API / RSS（如可用）/ 人工收集；Discourse 按站点许可读取；不突破登录墙 | 条件 A |
| 同口径公开讨论趋势 | 固定网站白名单、固定查询模板、固定日期窗口及采样频率 | B |
| 研究期刊与公开调查 | PubMed / Semantic Scholar + IFIC、CDC、KFF 等公开调查报告，人工精读后入库 | B |
| GitHub 开源生态 | 检索相关开源项目、Issues 与讨论 | C |
| 自有问卷回收 | 工作台生成的问卷回收后按统一表回灌 | A |
| Amazon 评价与 Q&A | 只走 §4.3 四条窄路 | 初步 |
| 内部客诉（CX） | 离线导入，入库前匿名化，不直连任何第三方接口 | C |
| 用户上传 CSV | 导入口：映射统一表字段后入库并留导入记录 | 随原始来源定级 |
| YouTube 评论（扩展主线） | YouTube Data API：按相关视频检索并取 commentThreads / replies | 条件 A |
| Reddit（备用） | 独立适配器；只在授权或服务可用时接入，失败不阻断搜索/CSV | 条件 A；来源内独立报告 |

### 4.3 Amazon 的四条窄路

| 窄路 | 做法 | 定位 |
|---|---|---|
| 自有产品后台导出 | Seller Central / Brand Dashboard 的 Customer Reviews 里人工查看、筛选、导出；或 Vine、Request a Review 官方回流 | 合规 · 手工量 |
| 公开页人工采样 | 浏览器人工打开公开产品页，记录页面可见的精选评价与 Q&A，逐条留 URL 与截图 | 合规 · 小样本标注 |
| 只取聚合数 | 记录星级分布、评价总数、价格等聚合字段，做竞品盘子对照，不碰评论文本 | 合规 · 只做背景 |
| Shulex API（第三方 VOC 服务） | 通过 Shulex 评价分析接口取得结构化评价结果，导出后按手工 CSV 通道入统一表，批次来源登记为 Shulex | 初步 · 依赖服务方 |

### 4.4 Reddit 备用通道与来源快照原则

Reddit 仅为可选补充接入器，遵守当期平台授权及实际可用性；不以其持续在线作为 P0 的验收前提。时间线（2026-11-23 核查）：

- 未登录 `.json` 自约 2026-05-30 起返回 403；
- 2026-09-30 官宣、2026-10-31 起不再接受新的公开 API 接入申请；
- RSS 自 **2026-11-13 起停止支持**（不是当天断流，官方不再承诺可用性，实测限流严重）——PDT 写"停止支持、无可用性承诺"，不要写"已关闭"；
- **2027-01-12 起，未在开发者平台注册的应用开始被撤访问权**——若 P0 依赖 Dialog MCP / Arctic Shift 等兜底通道，必须在 2027-01-12 前确认其注册与通道状态，不能只盯 2027-03；
- **2027-03 公开 Data API 全面关闭**。

所有来源都必须保存采集批次、原文或获准保留的证据、URL、发布时间、采集时间及抓取方法。来源不可用时允许使用已获授权的快照复跑；不应尝试绕过登录、验证码、访问控制或站点限制。

### 4.5 跨网站搜索的"发现 → 取证 → 采纳"契约

Search API 负责发现 URL；平台 API/许可页面读取负责提取用户原话；数据质量门决定是否可进入统计。搜索结果摘要、新闻、评测和广告内容不能作为用户声音混入同一分母。P0 建议覆盖目标（设计门槛而非已完成结果）：至少 100 条去重且可核验的真实用户语义片段，尽量来自 ≥3 个独立站点/来源批次；来源数量不足时降级为探索性结论，不能伪称"全网代表性"。

## 5 总体架构：六层

形状借 AWS 开源示例 sample-voice-of-customer-datalake 的三段管线（存原始 → 富化 → 聚合），中间插入它没有的发现层，末端接问卷输出与回流。

| 层 | 职责 | 关键组件 / 动作 | 输入 → 输出 |
|---|---|---|---|
| 1 采集层 | 每个来源一个接入器，互不影响 | AI 搜索规划器；Tavily + Brave 双搜索发现；YouTube/开放论坛适配器；Reddit 备用；CSV 人工导入 | 研究问题 → URL 候选 → 经许可的原文批次 |
| 2 原始层 | 原文原样落盘，永不覆盖 | 原话/URL/检索式/时间窗/源类型/采样批次/提取许可/剔除原因入库 | 批次 → 可重跑的原始语料库 |
| 3 发现层（P0-1） | 从无标签语料提出清单外新意图候选 | BERTopic + TopicGPT 四步；新意图与原注册表比较；人工确认及"本轮无新意图"的真实输出 | 原始语料 → 候选意图 → 意图注册表新版本 |
| 4 执行层（P0-2） | 意图给定后规模化编码 | Jev Choice / Score / Noul；金标准与概率落库；Token Center 预估与余额闸门；失败重试和缓存 | 语料 + 注册表 → 带完整概率分布的编码结果 |
| 5 仪表盘层 | 把编码结果变成可操作洞察 | 情感 / 问题 / 趋势 / 推荐四模块；来源 / 时间 / 意图 / 置信度筛选；每张指标卡带分母与日期 | 编码结果 → 洞察页面与推荐清单 |
| 6 输出层 | 把发现变成问卷与报告，并回流 | 问卷生成器导出 Google Forms；洞察报告按「结论 → 证据 → 原文链接」导出；问卷回收回灌第 2 层 | 发现与洞察 → 问卷 / 报告 → 回收数据回流 |

架构原则：先存原始、再谈分析；自家数据与竞品数据分开算；改分类（意图注册表）后可全量重跑；工作台核心动作（检索、编码、汇总、出题）都留程序接口，可被后续自动化调用，而不是锁在一个网页里。

## 6 Jev 执行层规格（强制项）

**强制声明：执行层必须使用 Jev 落地。**任何以通用大模型直接分类、关键词规则或人工逐条编码替代 Jev 的实现，都不算完成 P0-2：不进入验收、不计入分期完成度。替代或降级使用 Jev 必须先在第 14 章决策记录里取得明确拍板，并同步修订本章。

### 6.1 Jev 是什么

Jev 是 TypeSafe AI 于 2026-09-15 推出的 System One 决策模型，「非结构化状态进，带概率的类型化决策出」——不生成文本，只做带概率的判断。训练方式 RLCD。调用：`POST https://api.typesafe.ai/v1/systemone`，body 为 `state` + keyed `questions` 对象（不是 list，list 会报 422）；API key 经 `TYPESAFE_API_KEY`。价格：输入 $0.042/百万 tokens，输出免费。上下文：整请求 64k tokens、单个问题 32k；加 `TypeSafe-Danger-Zone-Long-Context: true` 可到 262k，但更慢、更不准，P0 不用。

**版本锁定（硬规则）：** P0 锁定模型版本 `jev-1.14.0`（2026-10-14 发布），禁止使用别名 `jev-latest`——别名会随版本更新改变行为，已校准的阈值可能静默失效。任何版本变更（含小版本）都必须重跑 100–200 条金标准、重新报告一致率并重定阈值后才可放量，变更与复核结果写入校准记录。上线前以 TypeSafe 控制台显示的实际版本再复核一次（公开文档页口径曾有 1.13 / 1.14 不一致）。

**Box 明确排除：** Jev 1.14 新增第四种问题类型 Box（在图片中定位物体并返回边框分数）。本工作台处理的是文本 VOC，Box 不在 P0 范围内，执行层不得把 Box 当作图片理解能力接入；含图片的帖子在 P0 只取其文字部分，图片内容不编码。

### 6.2 三种判断的规格

| 判断 | 用途 | 输出（必须落库） |
|---|---|---|
| Choice | 意图分类：这条内容的用户到底想干什么 | 每个选项的概率（完整分布，不只存第一名）+ 第一名意图编号 |
| Score | 语言打分：按有序量表评估强度与情绪 | 各档概率 + 概率加权分（逐项存，不合并成一个总分） |
| Noul | 问题检测：清单里每个问题是否在这条内容中成立 | 逐项 0–1 概率（每项独立存；Noul 没有 confidence 字段，阈值直接打在概率上） |

- 编码单位是 mention 级：一句话或一个语义段一个编码单位，而不是整帖一个标签。
- 无原文引用不成立：每条编码必须挂回原文片段与链接；挂不回的编码直接丢弃，不进统计。
- 完整分布落库：Choice 存全部选项概率，Score 存各档概率，禁止只存最终标签。
- **None 兜底（硬规则）：每个 Choice 的选项清单必须包含一个 None 选项**（「以上都不是 / 不属于任何现有意图」）。Jev 的 Choice 总会选出一个选项，即使正确答案不在清单里；独立评测（EurekaLeo 调查，2026-10-07 截止，101 项核心研究）显示，即便给了明确的 None 选项，Jev 也只在约 7% 的缺失正确答案菜单上拒绝作答——所以 None 是必要条件，但单独不够，必须与下一条守门配合。
- **Noul 守门（硬规则）：每条编码另加一道 Noul 判断**——「这条内容是否属于现有意图清单？」概率低于守门阈值的条目，不按 Choice 第一名入库，一律进发现层候选池，作为新意图信号。没有这道守门，新意图会被硬塞进旧框，P0-1 的发现机制即告失效。

### 6.3 金标准与校准流程（放量前置条件）

1. 建金标准集：从首批语料中抽 100–200 条，由人工按注册表定义逐条标注；先标约 50 条定规范，其余按规范扩充。
2. 测一致率：Jev 输出与金标准逐条比对，分别报告 Choice 意图一致率、Score 分档一致情况、Noul 逐项一致率；不达标先改定义与量表，不先改阈值。
3. 定阈值：按一致率结果为三类判断分别设定置信阈值；阈值与版本写入校准记录，与注册表版本绑定。
4. **中文单独校准：**中文语料（及中英混排）单独抽金标准、单独测一致率、单独定阈值，禁止用英文校准结果直接套中文。依据：Chinese-Jev（arXiv:2609.36965）指出既有 Jev 模型中文决策准确度有限，并为此另行训练中文模型；TypeSafe 亦称英语最强、CJK 等语言支持但准确度不等。禁止用英文翻译后跑分代替中文原文跑分。
5. 滚动扩充：复核队列的人工结论持续回流金标准集；每次注册表大版本变更后重新校准。

### 6.4 低置信与复核队列

Choice 最高概率低于阈值、Score 分布过平、或 Noul 关键项概率落在灰区间的条目，自动进入人工复核队列，不直接进入任何统计。复核队列同时是发现层的输入。队列长度与平均等待时长上仪表盘。抽查纪律：每批自动编码随机抽查 20 条人工核对，正确率低于约 80% 时该批结果标注「谨慎使用」，细格样本少于 10 条的分组显示「数据不足」而不给百分比。

### 6.5 Jev 层的输入输出契约

输入：待编码文本单位 + 注册表版本 + 量表与问题清单版本，必须带 record_id 与段序号；版本缺失的请求拒绝执行。输出：intent_probs（完整分布）、scores（逐项分布与加权分）、issues（逐项概率）、置信标记、review_status，按第 8 章字段落库；原始概率永不覆盖。失败处理：调用失败或返回不完整分布的条目标记为待重试，不以默认值填充；重试仍失败进复核队列并注明原因。数据边界：内部客诉等敏感数据匿名化后处理；是否可调用外部 Jev 服务按第 14 章隐私口径拍板执行，未拍板前内部数据不调用任何外部服务。

### 6.6 Jev 层验收门槛（P0-2 Done 的定义）

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| J-1 | 三类判断全部上线 | Choice / Score / Noul 三种判断均在试点语料上实际运行，缺一类不算完成 |
| J-2 | 金标准校准完成 | 100–200 条金标准标注完成，一致率有书面记录，阈值已设定并与注册表版本绑定 |
| J-3 | 中文单独校准 | 中文语料有独立金标准子集与独立阈值 |
| J-4 | 完整分布落库 | 抽查编码结果，概率分布完整可查，无只存最终标签的记录 |
| J-5 | 复核队列运转 | 低置信条目 100% 进队列，无低置信条目直接进入仪表盘统计 |
| J-6 | 引用可点回 | 抽查 20 条编码，每条可点回原文片段与来源链接；点不回的已按规则丢弃 |
| J-7 | 额度条可用 | 真实成功请求后以 X-Tokens-Remaining 更新余额；没有数据则显示"未同步"；单次 usage.input_tokens 正确落库 |
| J-8 | 补充额度与预算保护 | 跳转供应商购买页；402 停止新任务，支持批量预计成本、告警、Key/限流/上游错误分流与幂等重试 |
| J-9 | 版本锁定执行 | 全部调用记录 model_id = jev-1.14.0，无 jev-latest 调用；版本变更留有重跑金标准与重定阈值的记录 |
| J-10 | None + Noul 守门生效 | 抽查全部 Choice 配置均含 None 选项；守门 Noul 已上线，答否条目 100% 进发现队列、无一按 Choice 第一名直接入库 |

### 6.7 Jev Token Center：额度条、购买入口与批次预算（P0 必做）

目标：用户在任何页面都能看见 Jev 的"账户可用余额 / 本次消耗 / 本批预计消耗 / 额度状态"，并可点击"补充额度"。所有数值区分"供应商返回的已同步余额"和"本地估算值"，禁止用假的实时余额。

功能与验收（TC-01~TC-08）：全局顶部常驻 Jev 额度条；余额同步优先解析成功响应头 `X-Tokens-Remaining`，记录 `usage.input_tokens`；「刷新状态」不存在可验证 balance API 时不得伪造"实时刷新"请求，可手动同步账面余额；点击「补充额度」打开 https://jevmodel.org/zh/pricing/ 或该供应商的账户购买页，工作台不收款、不保存银行卡、不声称已充值；额度闸门：批量任务开始前估算所需 tokens，不足时阻止新批次并允许缩小批量；余额预警 <20% 提示、<5% 高危；402 标"余额不足"、401 标"Key 异常"、429 按限流、502 上游错误重试；本地用量明细按批/模型/注册表版本/重试记录；Key 只保存在服务端环境变量/密钥存储；支持多提供商适配器，预算隔离。

### 6.8 Token Center 数据接口与账本字段

provider_remaining_tokens（响应头 X-Tokens-Remaining，优先级高于本地相减估算）；request_input_tokens（每次成功响应 usage.input_tokens 为计费单位）；local_estimated_remaining（最近一次已同步余额 − 同一 Key 后续本地成功调用用量，仅估算）；quota_baseline_manual（用户从供应商 Dashboard 人工输入余额，标"手动"）；run_estimate（试运行实际单条 token 均值 × 计划编码单位数 × 安全系数 1.3）；billing_redirect（"补充额度"跳转供应商定价/购买页，不作为充值成功凭证）；provider_adapter（P0 第三方 jevmodel.org；保留官方 TypeSafe 适配接口；两者 Key 和计费单位不同，不得混算）。

官方 TypeSafe 直接计费时，供应商控制台显示的是货币余额（非同一 100,000 Token 赠送池）；UI 适配器必须按提供商展示正确单位，不允许把不同平台余额相加。公开资料未确认 jevmodel.org 提供可由 API Key 调用的独立只读余额端点，因此 P0 以成功响应头和供应商 Dashboard 为可信数据源。jevmodel.org 为独立第三方服务，不等同 TypeSafe 官方；内部未公开 VOC 原文默认不得发送至该第三方。

### 6.9 已知限制与数据边界（硬规则）

- **CX 绝不进 Jev（绝对禁令）：** Jev 走 TypeSafe 托管 API，jevmodel.org 更是独立第三方——两者都属「第三方服务」。内部客诉（CX）只做本地/人工编码，绝不发送到 Jev 或任何第三方模型服务，不设例外；Jev 只跑公开站外内容与公开来源 CSV。
- **留存口径不得写过头：** 不得把「供应商不使用客户数据训练」表述为「数据不留存」。有 2026-09-23 核查记录称零留存（zero retention）仅限企业版计划；上线前必须在 TypeSafe 控制台确认所购计划的留存条款，并把结论回写本节。
- **计数与日期不可靠：** Jev 对计数与日期比较不可靠；涉及条数、日期先后、时长等判断的编码项，不直接采用 Jev 输出，须以规则校验或人工复核为准，并在校准记录中标注。
- **高置信也要抽查：** 放在 state 里的原文可能左右 Jev 判断。复核不能只看低置信条目；§6.4 的每批 20 条抽查须覆盖高置信样本，高置信错判要回溯同批结果。
- **选型锁定与重访触发：** 锁定 Jev 的理由是已完成评估、同类决策 API 中成本最低（官方价 $0.042/百万输入 tokens，输出免费）、且为先行者；P0 不重开选型。出现以下任一情况才重访：Jev 涨价、中文校准一致率不达标、或官方中文模型发布。按每条样本约 300 输入 tokens 粗算，1,000 条跑一整套问题约 **$0.013**，P0 试点 Jev 直接成本可忽略，真实成本在人工标注与复核。

## 7 发现层规格（P0-1）

### 7.1 发现流程（六步）

1. 已知先分掉：新语料先过执行层——用意图的向量表示做近邻召回、并由 Jev Choice 对现有注册表分类，能高置信归入现有意图的先分掉。
2. 残差进池：分不进去的残差、低置信条目、以及 Noul 判定「超出已有问题清单」的条目，持续进入候选池。
3. 双轨提候选：一轨用 BERTopic 对候选池聚类出主题簇；一轨按 TopicGPT 四步走（生成主题 → 合并理顺 → 逐条分配且必须附引用原话 → 自检纠错）。两轨结果互相校验，只在一轨出现的候选标注「单轨信号」。
4. 开放编码起草：生成模型对候选簇做开放编码，起草候选意图：名称、定义、包含/排除标准、触发原话、与现有意图的区别。
5. Jev 验证候选：用 Jev 测候选意图的覆盖率与区分度；覆盖太低或不可分的候选退回合并或拆分。
6. 人工确认入表：研究者命名、合并或拆分后，候选意图进入意图注册表并升版本；未通过的候选保留在池中并注明原因，不删除。

### 7.2 意图注册表

每个意图一条记录：intent_id / 版本号（定义变更升小版本，清单结构变更升大版本）、名称与定义、包含/排除标准（各配至少 1 条边界例）、代表原话（至少 3 条原文片段 + 链接）、首次发现日期 / 证据 n 与来源（按来源分开）、验证状态（未验证 / 问卷验证中 / 已验证 / 未通过）、变更记录（合并、拆分、改定义的日期、原因与前后版本对照）。

### 7.3 发现的触发方式

批次触发（每批新语料入库后自动跑一轮残差筛查）、声量触发（某话题声量陡升或新话题冒头时触发一次发现层重跑）、巡检触发（P2 起按固定节奏如双周做发现层巡检）。

### 7.4 发现层验收（P0-1 Done 的定义）

产出候选意图清单 v1，使用预先构建的"已知 + 未知"盲测集证明新意图可被识别、拒绝或合并；真实样本中若无可靠新意图，明确记录"本轮未发现"。每个被采纳的新意图均需人工确认、n、代表原话与区分依据。候选池、残差队列、单轨信号均有留痕；被否决的候选有原因记录。发现全程只用快照语料，可复现。

## 8 统一数据表 Schema

所有来源先进这一张表再谈分析。字段分四组：溯源（record_id、source_type、source_url、published_at/collected_at、batch_id、search_query_id/engine、source_platform/content_role、extraction_method/access_policy）、原文（raw_text、lang、rating/verified、engagement）、编码（cluster_id、intent_id + intent_probs、scores、issues）、治理（evidence_grade、review_status、author_hash、raw_text_status/evidence_quality、dedupe_group/author_key_hash、source_scope/eligibility_reason）。编码组中的 Jev 字段为必填产出。CSV 导入最小字段：raw_text、source_type、published_at、source_url；评价类另加 rating、verified、产品型号。缺原文或来源的 CSV 不入库。机器可读定义见 `schemas/unified-table.schema.json` 与 `schemas/sampling-log.schema.json`。

### 8.1 采样日志

每批数据登记：来源、检索词或社区、时间窗、抓取方式、条数 n、剔除规则。任何数字被引用时必须能回溯到哪一批；不同口径的数字绝不并列引用。

### 8.2 脱敏规则

入库前自动处理：作者名哈希化；去掉订单号、邮箱、地址类字段。内部客诉默认禁止出境到任何第三方模型服务，只能在批准通道内处理。公开站外内容保留原文链接即可，不存作者画像信息。

## 9 仪表盘规格

四个模块集中在一页：情感分析、问题检测、趋势追踪、智能推荐。全局规则：顶部筛选器含来源、时间、意图、置信度阈值四项；每张指标卡必须带分母 n、统计时间窗与来源构成；所有数字按来源分开报，绝不混算一个「总体占比」；每条结论可点回原文与批次。

- **情感分析：** 满意度、挫败感、信任度由 Jev Score 分别输出，不合并成一个正负总分；默认视图是「意图 × 情感」矩阵；细格样本少于 10 条显示「数据不足」。
- **问题检测：** Jev Noul 问题清单逐项概率；只显示同一来源、同一分母内的提及率与命中条目的平均严重度；跨来源只并列展示，不相加、不平均。
- **趋势追踪：** 每个话题先攒 4 周同口径基线，趋势图只含同口径序列；标注新出现与声量陡升的话题，可一键触发发现层重跑；趋势只认 published_at。
- **智能推荐：** 每条推荐必须带齐四件套——触发条件、证据（n、来源构成、至少 1 条代表原话链接）、建议动作（带状态流转）、验证方法；缺一不展示。
- **待审队列视图：** 队列长度、来源构成、平均等待时长、近 7 天处理量；长期积压即数据质量告警。
- **洞察报告导出：** 痛点、机会、风险、行动建议四段；每条结论带代表性引用原文与链接。
- **全局额度条与采样漏斗：** 全站顶部右侧固定显示 Jev 额度条；采样漏斗：搜索命中 URL → 可访问页面 → 提取成功原话 → 去重后候选 → 研究纳入 n → Jev 编码成功 n → 待人工审核 n，每一级都有分母、数量、被排除原因。

## 10 问卷输出模块规格

问卷不是把洞察改写成问题，而是给每个发现配一种验证方式。生成器按 10.1 的映射表出题，人工只做删改与排序，最后导出 Google Forms 投放；回收数据按统一表回灌，验证或推翻发现。

### 10.1 发现类型 → 题型映射

| 发现类型 | 要验证什么 | 生成题型 | 示例（营养秤场景） |
|---|---|---|---|
| 新意图候选 | 这个意图在目标人群里是否真实存在、多普遍 | 场景多选题（选项 = 意图清单 +「其他」开放兜底） | 「你最近一个月用厨房秤主要是为了？」 |
| 意图间优先级不明 | 多个意图同时成立时，用户先为哪个买单 | 二选一迫选题 / 排序题 | 「秤上直接看营养」与「称得更准」二选一 |
| 高严重度问题 | 论坛里骂得凶的问题，是个例还是普遍摩擦 | 经历 + 困扰度量表题（遇到过吗 → 多困扰 0–4） | 「用 App 记录时遇到过同步失败吗？」+ 困扰程度打分 |
| 换用 / 放弃信号 | 切换成本与触发点 | 换秤意愿题 + 触发条件多选 | 「什么情况下你会换掉现在的秤？」 |
| 清单外空白 | 给下一轮发现留入口 | 每份问卷固定 1–2 道开放题，回收后直接进发现层语料 | 「称量时还有什么让你觉得麻烦的事？（选填）」 |

### 10.2 出题纪律

选项必须来自原话归纳，不凭空编场景；每个选项挂证据条数与代表原话，可点回。一道题只验证一个发现。需求排序借 ODI 框架：按「重要性 × 当前满足程度的缺口」排优先级。讨论声量可转成投票选项作题项候选来源，但站内投票结果不等于目标人群分布。多选题的「最多选 N 项」在题面写清；回收分析时剔除超选回答（Forms 本身不强制限选）。人口题只放一道、非必填、置于问卷末尾；不收集邮箱，保持匿名。预估答案必须标「估计」。

### 10.3 发布流程（四道门）

1. 机器预检：用模拟人格对问卷做预测试，抓题面歧义与作答分布异常；预检只覆盖题面问题，不代替真人。
2. 真人试填：先找 2–3 人试填，确认能打开、能理解、时长在预估内；试填答卷在正式投放前清除。
3. 正式投放：只分享问卷填写链接；投放渠道与招募方式登记进采样日志。
4. 回收回灌：回收数据映射统一表入库，样本来源与招募方式随批次登记；小样本只报分布。

### 10.4 回流闭环

每个被问卷验证过的意图，在注册表里更新验证状态：达到预设验证标准的标「已验证」；未通过的降级、拆分或退回候选池，并记录原因。问卷的开放题答卷直接成为发现层的新语料——问卷既是验证出口，也是下一轮发现的入口。

## 11 对标借鉴清单

两批共 16 个对标的共同结论：市面方案几乎都只做「执行」；做到「发现新意图」的只有机制级参考，做到「发现转问卷」的只有一个（ProductWeaver）。借：AWS 三段管线与 Radar 分开算；Dialog Reddit MCP 作 Reddit 接入层；jordanburke reddit-mcp-server 作第二接入（Arctic Shift 档案兜底）；BERTopic 作发现层聚类引擎；TopicGPT 四步流程；IntentGPT 残差机制；ProductWeaver 问卷三条纪律；Waters 四条治理规则；Qiaomu 洞察报告模板；Obsei 接入插件形态与新主题提醒；Consensus 声量→投票选项；Automated Questionnaire Pretesting 模拟预检；ProduckAI 工具化形态；Dovetail 证据链标准；Thematic/Chattermill 注册表治理；Productboard/Canny 推荐形态。不借：整套云栈重量与预定义分类法；不采购商业平台；聚类/主题结果不直接当意图发布；k-anonymity 阈值不进发现层。完整对照见专案第 4 节与 `docs/benchmarks.md`。

## 12 分期计划与验收

三期推进。P0 不再绑定 Reddit：先实现 CSV + 全网两种搜索发现渠道 + 至少一种合规原文提取方式 → 发现层与 Jev 校准 → 可追溯问卷 → Jev Token Center。P0 的技术验收与研究发现分开判断；真实语料即使没有新意图，也不得强造结论。

- **P0 窄链跑通：** 统一数据表与采样日志；CSV 可导入 + 100 条去重真实用户语义片段入库；Tavily/Brave 中至少两条可替换搜索发现通道；至少一条论坛/YouTube/许可页面正文提取通路；发现层试点（BERTopic + 开放编码 + 人工确认，盲测集验证）；Jev 执行试点（100–200 条金标准，J-1~J-10 通过）；问卷生成器 v1；Jev 额度条与购买入口；故障与数据质量演练。
- **P1 仪表盘与声量：** 仪表盘四模块上线；声量基线攒满至少 4 周；第二声源与期刊证据层入库；低置信队列日常运转；至少一份问卷完成回收并回灌，注册表回写验证状态。
- **P2 扩展与对照：** 竞品 Radar 独立跑通；Amazon 窄路常态化；GitHub 领先信号纳入季度三角验证；持续监控巡检。

## 13 风险、合规与红线

方法论红线：定性不推比例；Jev 概率 ≠ 准确率；口径一致才可比；证据可点回；旧款不套新款；模拟不冒充真实。合规与数据边界：Amazon 不爬；所有来源按许可快照与证据追溯，禁止绕过访问控制；内部数据不出境（内部客诉先匿名化再进系统，不直喂任何第三方服务，只做痛点排序）；GitHub 只作信号。主要风险与应对：单一搜索引擎/站点不可用（双搜索渠道 + CSV 回退）；全网搜索的选择偏差（固定查询/来源分层、抽样日志）；Jev 校准不达标（先改定义与量表再调阈值，中文单独金标准）；发现层产出伪意图（双轨互校 + Jev 覆盖率/区分度验证 + 人工确认）；小样本被读成用户比例（细格 <10 显示「数据不足」）；问卷回收样本偏差（招募方式随批次登记）；Jev 第三方余额/Key/购买风险（按响应头同步、仅外链购买、Key 服务端保管）；供给商更换成本（Provider Adapter 抽象，分开账本）。

## 附录 D Jev 额度条的 UI 状态文案

未配置 Key（Jev 未连接；余额 — / 未同步）；已连接未同步（等待首条成功请求回填）；正常（显示余额、消耗、上次同步时间；绿色进度条）；低余额（<20%，黄色）；临界（<5%，红色，禁止超过预算的批次）；402（余额不足）；401（API Key 无效或失效）；429/502（限流或上游异常，保留任务为待重试）；已购未同步（已打开购买页；未收到额度变化确认）。
