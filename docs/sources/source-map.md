# 来源全景表

每个来源标注四件事：怎么接、回答什么问题、证据等级、口径红线。证据等级：A = 可作主要依据；B = 对照与三角验证；C = 只作信号 / 痛点排序，不推比例。

| 来源 | 接入方式 | 回答什么问题 | 证据等级 | 口径红线 |
|---|---|---|---|---|
| 全网公开讨论（核心发现入口） | Tavily + Brave 等搜索 API：AI 生成查询组合、发现 URL；按站点权限获取原文。搜索结果自身不等于有效 VOC | 发现跨网站的用户真实任务、抱怨、替代方案与新意图线索 | 条件 A：原话可核验；否则 C 线索 | 每个站点/时间窗分别报 n；点赞与评论数只作曝光/声量参照，不当满意度 |
| 垂直论坛 / 开放社区（主线原话） | 可访问的论坛官方 API / RSS（如可用）/ 人工收集；Discourse 按站点许可读取；不突破登录墙 | 长期使用场景、持续摩擦、换用与放弃原因 | 条件 A | 抓不到全文的用原文片段 + 链接并注明受限；不把单帖热度当普遍程度 |
| 同口径公开讨论趋势 | 固定网站白名单、固定查询模板、固定日期窗口及采样频率 | 网站内相对趋势，仅为信号，不推全网用户需求规模 | B | 只能比较同一平台/相同查询模板/相同检索窗口/相同采样频率下的变化 |
| 研究期刊与公开调查 | PubMed / Semantic Scholar 等开放检索 + IFIC、CDC、KFF 等公开调查报告，人工精读后入库 | 人群基线与行为背景 | B | 期刊结论是人群层面证据，不直接证明本品类用户占比；引用标明样本与年份 |
| GitHub 开源生态 | 检索相关开源项目、Issues 与讨论 | 领先 / 技术型用户想要什么、现有产品哪里不够用以至于自己动手 | C | 只作趋势前哨，可与调查、评价三角验证；不进漏斗、不推规模与付费意愿 |
| 自有问卷回收 | 工作台生成的问卷（Google Forms）回收后按统一表回灌 | 验证发现：某意图在目标人群里是否真实存在、多普遍、优先级如何 | A | 样本来源与招募方式必须登记；小样本只报分布不报「用户占比」 |
| Amazon 评价与 Q&A | 只走四条窄路（见 amazon-narrow-paths.md） | 已购用户的产品体验与具体抱怨——体验验证，不作发现主线 | 初步 | 只用 US verified 评价作产品体验依据；样本量与采样方式逐批登记 |
| 内部客诉（CX） | 离线导入，先匿名化再进系统，不直连任何第三方 API | 痛点排序：哪些问题最让现有用户受不了 | C | 内部数据纯负面，不推满意度与比例；原始表不外传、不喂第三方工具；**绝不进公开仓库** |
| 用户上传 CSV | 工作台导入口：任意来源的评价 / 评论 CSV，映射到统一表字段后入库，留导入记录 | 把已有存量数据接进同一套发现与执行流程 | 随原始来源定级 | 来源不明的 CSV 不定级、不进统计；最小字段见 schemas/unified-table.schema.json |
| YouTube 评论（扩展主线） | YouTube Data API：按相关视频检索并取 commentThreads / 可取得的 replies；按频道与发布时间留痕 | 真机操作、测评下方真实用户抱怨与对比讨论 | 条件 A | 真实评论可追溯 |
| Reddit（备用） | 独立适配器；只在授权或服务可用时接入，失败不阻断搜索/CSV；已存快照可离线复跑 | 补充细分人群讨论和历史讨论信号 | 条件 A；来源内独立报告 | 只信快照，见 reddit-timeline.md |

## 跨网站搜索的"发现 → 取证 → 采纳"契约

Search API 负责发现 URL；平台 API/许可页面读取负责提取用户原话；数据质量门决定是否可进入统计。搜索结果摘要、新闻、评测和广告内容不能作为用户声音混入同一分母。P0 建议覆盖目标（设计门槛而非已完成结果）：至少 100 条去重且可核验的真实用户语义片段，尽量来自 ≥3 个独立站点/来源批次；来源数量不足时降级为探索性结论，不能伪称"全网代表性"。
